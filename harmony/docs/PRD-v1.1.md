## 2. 变更背景与用户诉求原文

### 2.1 背景

应用 v1.0 已完成并通过内部验收，但存在三类问题：① 应用内保留着 3 处「即将上线」的假入口（多账本 ×2、备份恢复、记账提醒），形成空承诺交互，也违反旧 PRD 6.3 驳回点 16「描述中的功能未实现」的风险导向；② 用户实测反馈「导出数据显示失败」，实际是导出链路把真实失败与用户取消一律静默吞掉，用户既得不到失败提示也无法定位原因；③ 应用无任何网络能力，「意见反馈」入口仅能展示一个邮箱字符串，无实际价值。

### 2.2 用户诉求原文（唯一需求来源）

> 1. 把应用里的「意见反馈」入口删掉。
> 2. 用户反馈「导出数据显示失败」，要修复。
> 3. 应用里目前有 3 处「即将上线」的假入口（多账本、备份与恢复、记账提醒），全部要做成真功能。

### B · F-10.2 导出链路修复（P0）

**缺陷定位（现状）**
`ExportService.exportViaPicker`：
- `fileSuffixChoices: ['CSV 表格|.csv']` 格式不稳妥，可能触发保存面板参数异常；
- `catch` 把「保存面板异常/真实失败」与「用户取消」统一按取消静默返回，`FileUtil.copyToUri` 失败同样被吞——用户看不到任何反馈，即用户口中的「导出数据显示失败」。

**需求规则**
1. **取消（静默）**：`picker.save()` 返回空数组 → 静默返回，无任何 Toast；
2. **失败（明确提示）**：写沙箱临时文件失败、save 抛出非取消异常、`copyToUri` 失败 → Toast 展示明确失败文案（`ErrorMessages.EXPORT_FAILED`），并写 `LogUtil.e` 留排查痕迹（区分失败点：建临时文件 / save / 拷贝）；
3. **成功（明确确认）**：拷贝成功 → Toast「导出成功，共 N 笔」；
4. **picker 参数修正**：`fileSuffixChoices` 改为 `['.csv']`；
5. 行为语义不变：仍是 DocumentViewPicker 免权限保存、UTF-8 BOM、9 字段 CSV；「本月/全部」选择与文件名规则不变。

**验收标准（可测）**
1. 正常导出：出现成功 Toast（含条数），目标位置存在可被 Excel 打开的 CSV；
2. 在保存面板点「取消」：返回列表页，无任何 Toast；
3. 模拟写盘失败（如磁盘写满场景）：出现失败 Toast，文案为明确的失败提示而非静默；
4. 保存面板正常弹出且无因 `fileSuffixChoices` 导致的异常；
5. 导出全程不申请任何权限（延续零权限链路中的 Picker 方案）。

### C · 多账本落地（P0，对应 v1.0 F-2.5 / F-2.6）

**现状基础**：`ll_ledger` 表已建（SchemaConstants）；`ll_transaction / ll_account / ll_category / ll_budget` 均含 `ledger_id` 列且默认 1；`SeedDataManager` 预置默认账本；`MinePage.ets` ledgerGroup 首项与首页 `LedgerSwitcher.ets` 点击均为 `ledger_soon` Toast。

#### F-10.3 多账本管理（P0）

**功能规则**
1. 「我的 → 账本管理」进入账本管理页：账本列表（名称、图标、是否当前）；
2. **创建**：输入名称（1~20 字符，非空去重）、选图标（内置图标集）、选颜色；创建成功后自动预置一套与默认账本相同的系统分类（**默认裁决**，见 5.2），不预置账户；
3. **重命名/改图标/改颜色**：随时可改；
4. **删除**：仅允许删除「无流水账本」（该账本下无任何流水）；删除时在**单个事务内级联清理**该账本下的预算项、预算、分类、账户；删除前必须出现**「不可撤销」二次确认弹窗**，明确告知将连带删除该账本的账户/分类/预算等配置数据；默认账本（`is_default=1`）不可删除；系统始终保留至少 1 个账本；
5. 「我的页」账本管理条目 valueText 显示「N 个账本」（F-10.8）。

**用户故事**：见需求池 F-10.3。

**验收标准（可测）**
1. 可连续创建 ≥ 3 个账本，名称重复时被拒绝并提示；
2. 有流水账本点删除：被拦截（提示账本下存在流水不可删除），且不产生任何数据删除；
3. 无流水账本删除：先出现「不可撤销」二次确认弹窗，确认后删除成功，该账本下的预算项/预算/分类/账户被一并清理，且事务内执行（失败可整体回滚）；
4. 默认账本不出现删除入口；账本总数 ≥ 1 恒成立；
5. 新建账本自动拥有 11 支出 + 6 收入系统分类，可直接记账。

#### F-10.4 账本数据隔离与全局切换（P0）

**功能规则**
1. **当前账本持久化**：当前账本 id 存 Preferences，冷启动恢复；
2. **全局切换器**：首页顶部 `LedgerSwitcher` 点击弹出账本切换面板（列表 + 选中态），选择后全局生效并 `DataBus.bump()` 刷新；移除 `ledger_soon` Toast；
3. **数据隔离**：记账写入、明细列表、统计（环形/排行/趋势）、账户、分类、预算、CSV 导出、资产总览等全部按当前 `ledger_id` 过滤/写入；不同账本的流水、账户、分类、预算互不可见；
4. **余额与资产**：总资产卡仅汇总当前账本下的账户；
5. 所有既有 SQL 查询补齐 `ledger_id` 条件（现多数查询已带 `ledger_id = 1` 常量，改为动态当前值即可，架构师评估改造面）。

**验收标准（可测）**
1. 在账本 A 记一笔支出 → 切到账本 B：明细页看不到该笔，统计页金额不包含该笔；
2. 切回账本 A：该笔重新可见，金额一致；
3. 切换账本后记账：新流水写入当前账本（查库 `ledger_id` 正确）；
4. 冷启动后仍停留在上次选择的账本；
5. 账户管理/预算/导出页与当前账本一致；导出 CSV 的账本列为当前账本名。

### D · 备份与恢复落地（P0，对应 v1.0 F-6.3 / F-6.4）

**入口**：「我的 → 备份与恢复」新页面（移除 `mine_backup_soon` Toast），含「备份」与「恢复」两个动作。

#### F-10.5 本地备份（P0）

**功能规则**
1. 导出**全量业务数据**为**单个 JSON 文件**：`ll_ledger / ll_account / ll_category / ll_budget / ll_budget_item / ll_transaction` 全表 + 元信息（`app_version`、`schema_version`、`exported_at`、`row_counts`）；
2. 明文 JSON（默认裁决见 5.3），UTF-8 编码，含换行符校验字段（如行数或行数校验和）以便恢复前完整性初检；
3. 经 `DocumentViewPicker.save`（免权限，`fileSuffixChoices: ['.json']`）存到用户指定目录，文件名 `轻账本_备份_yyyyMMdd_HHmmss.json`；
4. 复用 F-10.2 修复后的三态语义：取消静默 / 失败明确 Toast / 成功 Toast（含总条数）。

**验收标准（可测）**
1. 有数据时点备份：生成 JSON 文件，含 6 类业务表数据与元信息，中文无乱码；
2. 成功 Toast 显示总条数；取消无 Toast；写盘失败有失败 Toast；
3. 全程零权限（Picker 链路）。

#### F-10.6 从备份恢复（P0）

**功能规则**
1. 入口 → `DocumentViewPicker` 选择 `.json` 文件（免权限）；
2. **选择后立即二次确认**：弹窗文案明确「恢复将覆盖当前全部数据，此操作不可撤销」，确认后才开始；
3. **安全恢复流程（默认裁决）**：先在沙箱解析与校验备份（结构、必填字段、`schema_version` ≤ 当前支持版本），校验通过后在**单个事务**内整库替换（清空 6 张业务表 → 写入备份数据 → 更新当前账本指针为备份中的有效账本），任何一步失败则回滚、现有数据不受破坏；
4. 校验失败（文件损坏 / 版本过高 / 结构不符）：Toast 明确提示，不进入覆盖流程；
5. 恢复成功：Toast 提示 + `DataBus.bump()` 全局刷新，返回后所有页面数据与备份一致。

**验收标准（可测）**
1. 备份 → 清空数据 → 恢复：流水/账户/分类/预算/账本全部还原，条数一致；
2. 恢复前必现覆盖警告弹窗，取消则不发生任何数据变更；
3. 篡改过的 JSON（截断/字段缺失）：提示校验失败，现有数据不变；
4. 备份 `schema_version` 大于当前支持版本：拒绝恢复并提示版本不兼容；
5. 恢复过程中途失败（如模拟写入异常）：库内数据回滚为恢复前状态。

### E · F-10.7 每日记账提醒（P0，对应 v1.0 F-7.3）

**功能规则**
1. 「我的 → 记账提醒」进入提醒设置页：**开关 + 时间选择**（默认 21:30）；移除 `mine_remind_soon` Toast；
2. 基于 `reminderAgentManager` 发布每日循环的本地代理提醒（通知标题「该记账啦」+ 正文提示，点击进入应用）；
3. 开启 → 发布提醒；关闭 → `cancelReminder` 取消；修改时间 → 先取消再按新时间重发；
4. **权限**：`module.json5` 增加声明 `ohos.permission.PUBLISH_AGENT_REMINDER`（系统授予型，声明即用，无运行时弹窗）。这是应用**首个声明权限**，需同步更新隐私政策与 AGC 声明（见第 6 章）；
5. 提醒状态展示（F-10.8）：我的页该条目显示「21:30 已开启」或「未开启」；
6. 边界：用户在系统设置关闭应用通知 → 提醒设置页保留开关状态，但给出「通知可能被系统关闭」的引导提示（尽力而为项）。

**验收标准（可测）**
1. 开启并设定 21:30 → 当日 21:30 收到本地提醒通知；
2. 关闭开关 → 次日不再收到通知；
3. 修改时间 → 按新时间触发，旧时间不再触发；
4. 杀进程/重启设备后提醒仍生效（代理提醒系统级行为）；
5. `module.json5` 仅新增该权限，无其他权限引入；拒绝/关闭通知不影响其余全部功能。

## 5. 待确认问题与默认裁决（不留空，均按默认裁决执行）

### 5.1 删除反馈邮箱后的审核风险兜底（F-10.1 连带）

**裁决**：应用内入口删除，但**上架资料与隐私政策文本中仍保留真实有效客服邮箱**。华为审核驳回点 5 针对的是「缺少客服/反馈渠道」——在 AGC 上架资料与隐私声明中提供邮箱即可满足，应用内入口并非唯一形态。若审核仍因「应用内无反馈入口」被驳回，回滚方案为：在「关于」页以纯文本（非入口项）展示邮箱，成本极低。

### 5.2 新建账本是否预置分类与账户（F-10.3）

**裁决**：**自动预置一套系统分类**（与默认账本一致：11 支出 + 6 收入），**不预置账户**。理由：分类是记账必选项，空分类会让新账本无法直接记账（破坏 3 秒记账体验）；账户是用户资产事实，不应替用户虚构。

### 5.3 备份文件是否加密（F-10.5）

**裁决**：**明文 JSON，不加密**。理由：与「纯本地、无账号」定位一致；备份文件存放在用户自选目录、由用户自行保管；加密会引入密钥丢失即数据不可恢复的新风险。在备份页注明「备份文件包含全部账目数据，请妥善保管」。

### 5.4 删除账本的数据处理（F-10.3）

**裁决（已更新，采纳架构口径）**：仅允许删除「无流水账本」；删除时在**单个事务内级联清理**该账本下的预算项、预算、分类、账户；删除前前置**「不可撤销」二次确认**弹窗；默认账本不可删、系统恒保留至少 1 个账本。
**调整记录**：原裁决为「仅允许删除空账本（无流水、无账户、无自定义分类、无预算）」。因新建账本会自动预置系统分类（见 5.2），任何账本几乎永远不满足「无分类」条件，按原口径实际无法删除任何账本，属不可执行的设计。故调整为架构师 T02 的实现口径（拦截码 `LEDGER_HAS_TX` 拦截有流水账本 + 事务内级联清理 + 二次确认）。**裁决人：主理人（采纳架构口径）**。数据安全保障不变：级联清理在事务内执行，且前置二次确认。

### 5.5 提醒权限是否违反「零权限」卖点（F-10.7）

**裁决**：接受从「绝对零权限」到「仅 1 项系统授予型权限」的演进——这正是 v1.0 PRD 6.1 已预写的 v1.1 红线路径（「不得为了保住零权限卖点而永久砍掉用户价值明确的功能」）。执行三点红线：① `PUBLISH_AGENT_REMINDER` 为系统授予型，无运行时弹窗，不打扰用户；② 关闭提醒/拒绝通知后全功能可用；③ 隐私政策、AGC 权限声明、`module.json5`、代码实际调用四处一致性同步更新。营销口径从「零权限」改为「默认零权限，仅在你主动开启记账提醒时使用系统提醒能力」。

### 5.6 当前账本指针与备份恢复的联动（F-10.6）

**裁决**：恢复完成后，当前账本指针重置为备份中 `is_default=1` 的账本（备份文件内不含 UI 状态），避免指针指向已不存在的账本 id。
