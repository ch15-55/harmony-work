## 优先找回原工程

在原开发电脑、备份、原 Git 仓库或团队成员工作目录中找 DevEco 工程。识别标志包括 `AppScope/`、`entry/src/main/ets/`、`entry/src/main/module.json5`、`build-profile.json5`、`oh-package.json5` 和 Hvigor 配置。这里仅列出常见标志，不代表已经拥有这些文件。

需要保留原有源码、资源、项目配置、Hvigor 脚本、依赖声明与锁文件，以及已有测试。不复制依赖缓存、build 输出、签名材料、设备数据和写有本机路径或密码的配置。

找回后先在原环境验证能够构建和运行，记录 DevEco、SDK、构建工具版本和实际命令，再接入本仓库。不要为消除错误而先升级全部依赖，也不要凭包内编译版本字段猜测完整环境。

## 源码接入方式

源码可编译并核对包名、版本和主要页面后，将真实工程作为仓库根工程接入；保留本次 `recovered/` 和 `docs/` 作为版本基线。若原工程也有 `README.md`、`AGENTS.md` 或 `.gitignore`，应合并规则，不能直接覆盖现有说明。

以下是接入完成后的结构示意，**这些工程文件当前并不存在**；具体路径服从真实工程：

```text
AppScope/                       # 原工程应用级配置和资源
entry/src/main/ets/
  ability/                      # 入口与生命周期
  pages/                        # 页面
  components/                   # 通用与业务组件
  viewmodel/                    # 页面状态
  service/                      # 业务、数据库、迁移、导出备份
  model/                        # 领域模型
  constants/                    # 集中常量
  utils/                        # 通用工具
entry/src/main/resources/       # 原始 strings/colors/media 等
entry/src/main/module.json5     # 原工程模块配置
build-profile.json5             # 去除本机签名和秘密后的共享配置
oh-package.json5                # 原工程依赖声明
```

提交前确保忽略规则覆盖实际生成物和本地签名配置。更新 README 的仓库状态、构建步骤和运行结果；只有成功构建并启动后，才能称其为“可运行工程”。

## 找不回源码时

保持当前资料仓库的准确说明。若后续决定依据产品需求重新开发，先明确范围、页面流程和数据模型，再用匹配环境创建真实 DevEco 工程，逐步实现并验收。

新写的实现应标明为“重新实现”，不能称为原源码恢复。当前模块清单可以帮助制定边界，但不值得为凑齐 103 个名称而复制文件数量；优先完成可靠的记账闭环，再扩展统计、备份和应用锁。
